This guide walks through setting up [Authentik](https://goauthentik.io) as the single sign-on provider for wg-easy — both for the web panel login and, optionally, for the LiveWireGuard app's provisioning flow.

All examples use sanitized placeholder values:

| Placeholder                       | Meaning                                          |
| --------------------------------- | ------------------------------------------------ |
| `https://vpn.example.com`         | The wg-easy panel URL                            |
| `https://auth.example.com`        | The Authentik instance URL                       |
| `<client-id>` / `<client-secret>` | Values generated by Authentik — never share them |

Requirements:

- Both wg-easy and Authentik are reachable over **HTTPS with a valid certificate** (wg-easy refuses OIDC servers without one).
- Access to the Authentik admin interface (`https://auth.example.com/if/admin/`).
- At least one working wg-easy admin account (needed to enable OIDC and to link accounts).

wg-easy uses standard OIDC: PKCE, scopes `openid email profile` and client authentication via `client_secret_post`. Authentik supports all of this out of the box.

## Overview: two OIDC clients

Two separate Authentik providers are involved:

| Client       | Type         | Used by                                                | Secret    |
| ------------ | ------------ | ------------------------------------------------------ | --------- |
| Panel client | Confidential | wg-easy web login                                      | Yes       |
| App client   | Public       | LiveWireGuard app ([Import guide](./livewireguard.md)) | No (PKCE) |

The App client is only needed if you use the LiveWireGuard provisioning endpoint; the panel works without it.

## Step 1 — Create the custom email scope mapping

Do this first, because both providers need it later.

1. Open the Authentik admin interface → **Customization** → **Property Mappings**.
2. Click **Create** and choose **Scope Mapping**.
3. Fill in:

    | Field       | Value                                               |
    | ----------- | --------------------------------------------------- |
    | Name        | `wg-easy verified email`                            |
    | Scope name  | `email`                                             |
    | Description | `email scope with email_verified: true for wg-easy` |

4. In the **Expression** field enter:

    ```python
    return {
        "email": user.email,
        "email_verified": True,
    }
    ```

5. Save. The scope name must be exactly `email` — it replaces the built-in mapping of the same name.

### Why this is required

Two reasons, one on each side:

**wg-easy requires a verified email.** Every OIDC login reads the userinfo response and rejects it unless it contains a `sub`, an `email` **and** a truthy `email_verified` — otherwise the login fails with `401 Email is not verified` (see `assertHasOauthProps` in `src/server/utils/oauth.ts`). The same flag matters for account matching: a token that only matches by email is only accepted for the LiveWireGuard endpoint when the email is marked as verified (see [User mapping](./livewireguard.md#user-mapping)). The `OAUTH_ALLOWED_DOMAINS` filter also runs on this email, so the login fails before any of these checks if the claim is missing or unverified.

**Authentik's default mapping sends `email_verified: false`.** Since Authentik 2025.10, the built-in `authentik default OpenID Mapping: email` hard-codes `email_verified` to `False`, because an email address alone does not prove the user controls it (before 2025.10 it was hard-coded to `True` — either way it is a fixed value, not the user's actual verification status). Authentik does not track email verification for directory accounts, so there is no real status it could report. The result: with the default mapping, wg-easy sign-in fails with `Email is not verified` even though the Authentik login itself succeeded — a very confusing failure mode, since the user did authenticate.

The expression above therefore asserts `email_verified: True` explicitly. That is honest as long as every account in the Authentik directory has a trustworthy email address (typical for company-managed directories where accounts are provisioned centrally). If that is not true for your directory, use a safer variant driven by a user attribute instead:

```python
return {
    "email": user.email,
    "email_verified": user.attributes.get("email_verified", False),
}
```

Then set the `email_verified` attribute per user or group in Authentik.

/// warning

Do **not** assign both the default email mapping and the custom one to the same provider — conflicting claims come from overlapping scopes. When a provider lists the custom mapping, remove `authentik default OpenID Mapping: email` from its scope selection.

///

## Step 2 — Create the panel provider (confidential client)

1. Admin interface → **Applications** → **Providers** → **Create** → **OAuth2/OpenID Connect**.
2. Configure:

    | Field                     | Value                                                              |
    | ------------------------- | ------------------------------------------------------------------ |
    | Name                      | `wg-easy`                                                          |
    | Authorization flow        | _Authorize Application (with consent)_ — the default explicit flow |
    | Client type               | **Confidential**                                                   |
    | Client ID / Secret        | Generated by Authentik — copy both now                             |
    | Redirect/Post Logout URIs | see below                                                          |
    | Signing key               | any available key (the default is fine)                            |

3. Redirect URIs — enter both, one per line:

    ```
    https://vpn.example.com/api/auth/oidc/callback
    https://vpn.example.com/api/auth/oidc/link
    ```

    - `.../callback` is used for the normal login.
    - `.../link` is used when an existing user links their account from the account page (see [Step 5](#step-5-link-accounts-and-first-login)).

4. Under **Advanced protocol settings** (depending on version: _Protocol settings_) → **Property mappings**, select:

    - `authentik default OpenID Mapping: openid`
    - `authentik default OpenID Mapping: profile`
    - your custom **`wg-easy verified email`** — and **remove** `authentik default OpenID Mapping: email`

Leave everything else at the defaults. Note the sub mode (`hashed_user_id` by default): wg-easy stores the token's `sub` claim to link accounts, so do not change the sub mode after users have linked — it changes every user's `sub` and silently breaks the links.

## Step 3 — Create the application

1. Admin interface → **Applications** → **Create** (or assign the provider to a new application if you created them separately).
2. Fill in:

    | Field    | Value     |
    | -------- | --------- |
    | Name     | `wg-easy` |
    | Slug     | `wg-easy` |
    | Provider | `wg-easy` |

3. Optionally restrict who sees/can use the application (a policy or group) — otherwise every Authentik user can log in to wg-easy, subject to [Step 5](#step-5-link-accounts-and-first-login)'s domain and auto-register settings.

The **slug** decides the issuer URL. With the slug `wg-easy` it is:

```
https://auth.example.com/application/o/wg-easy/
```

You can verify it any time on the provider's detail page (OpenID Configuration URL). The issuer from discovery must match this URL exactly — including the trailing slash.

## Step 4 — Configure wg-easy

Two equivalent ways; pick one.

### Option A — Admin panel (no restart)

Open **Admin Panel → OIDC** and fill in:

| Field         | Value                                             |
| ------------- | ------------------------------------------------- |
| Enabled       | on                                                |
| Display Name  | `Authentik` (button label on the login page)      |
| Issuer/Server | `https://auth.example.com/application/o/wg-easy/` |
| Client ID     | `<client-id>`                                     |
| Client Secret | `<client-secret>`                                 |

Changes apply immediately. The panel shows the two redirect URIs it expects under **Redirect URI** — compare them with Step 2. Empty fields fall back to the `OAUTH_OIDC_*` environment variables, and secrets are write-only (they are stored in the SQLite database, never displayed again). See [OIDC settings in the admin panel](./livewireguard.md#oidc-settings-in-the-admin-panel) for the full field reference.

### Option B — Environment variables

```yaml
environment:
    - OAUTH_PROVIDERS=oidc
    - OAUTH_OIDC_NAME=Authentik
    - OAUTH_OIDC_SERVER=https://auth.example.com/application/o/wg-easy/
    - OAUTH_OIDC_CLIENT_ID=<client-id>
    - OAUTH_OIDC_CLIENT_SECRET=<client-secret>
```

Optional hardening:

| Env                     | Example value | Effect                                                     |
| ----------------------- | ------------- | ---------------------------------------------------------- |
| `OAUTH_ALLOWED_DOMAINS` | `example.com` | Only allow email addresses at these domains                |
| `OAUTH_AUTO_REGISTER`   | `true`        | Auto-create accounts on first login (see warning below)    |
| `OAUTH_AUTO_LAUNCH`     | `oidc`        | Redirect straight to Authentik when opening the login page |
| `DISABLE_PASSWORD_AUTH` | `true`        | Disable password login entirely (see warning below)        |

/// warning | Auto registration

`OAUTH_AUTO_REGISTER` creates accounts with admin permissions (the permission system is not implemented yet). Only enable it if every user in the allowed Authentik application may administer wg-easy; otherwise leave it off and link accounts manually as described below.

///

/// warning | Access recovery

Before setting `DISABLE_PASSWORD_AUTH=true`, make sure at least one admin account has successfully logged in via Authentik. If no login method remains, the configuration has to be reset to regain access.

///

## Step 5 — Link accounts and first login

With `OAUTH_AUTO_REGISTER=false` (the default), the recommended rollout is:

1. Log in to the panel with your existing admin account.
2. Open your account page → **External Auth** → **Link** and sign in at Authentik. This walks through the `.../link` redirect URI and binds your wg-easy account to the Authentik user (`sub`).
3. Repeat for the other users, or enable `OAUTH_AUTO_REGISTER` if appropriate.

Matching works as follows:

- If the OIDC identity (`sub`) was linked before, login matches that account.
- Otherwise the account with the same **verified** email address is matched and linked automatically on login.
- Unmatched identities are rejected unless `OAUTH_AUTO_REGISTER` is enabled.

Verify: log out — the login page now shows an **Authentik** button, and signing in through it lands you back in the panel without entering a password.

## Step 6 — The LiveWireGuard app client (optional)

If you use the LiveWireGuard app, register a **second** provider as a public client:

| Field                     | Value                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Client type               | **Public** (no secret; the app authenticates with PKCE only)                                                              |
| Client ID                 | `livewireguard` (or your own — see below)                                                                                 |
| Redirect/Post Logout URIs | `com.wuxichaorongtechnologycoltd.livewireguard:/oidc/callback` (a custom scheme; Authentik accepts it as a redirect URI)  |
| Property mappings         | `openid`, `profile`, your custom **`wg-easy verified email`**, and **`authentik default OpenID Mapping: offline_access`** |

Notes:

- **`offline_access` matters here.** Authentik only issues refresh tokens when the provider has the default `offline_access` scope mapping assigned. Without refresh tokens the app cannot keep the user signed in and will prompt for login on every sync.
- **The custom email mapping matters here too.** A device that syncs for a user whose account has not been linked by `sub` yet is matched by email — and only when `email_verified` is true. Without the custom mapping such devices fail with `403 forbidden`.
- **Audience.** Authentik stamps the token's `aud` claim with the client id, so the default panel Audience (`livewireguard`) already matches. If you chose a different client id, set it under **Admin Panel → General Settings → LiveWireGuard → Audience**.
- Fill the new client id into **Admin Panel → OIDC → App Client ID** so the setup QR code shown on the home page provisions the app with this client (public client ⇒ no secret ends up in the QR code).

Details on the app side are in the [LiveWireGuard Import guide](./livewireguard.md).

## Troubleshooting

| Symptom                                  | Cause and fix                                                                                                                                              |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `401 Email is not verified` on login     | The default email mapping is still assigned. Swap it for the custom `wg-easy verified email` mapping (Step 1).                                             |
| `400 No email set` on login              | No `email` scope mapping assigned at all.                                                                                                                  |
| `401 Email domain not allowed`           | `OAUTH_ALLOWED_DOMAINS` does not contain the user's email domain.                                                                                          |
| `403 forbidden` from the app endpoint    | No wg-easy account matches the token (see [User mapping](./livewireguard.md#user-mapping)) — or the email claim is not verified.                           |
| Authentik shows `Redirect URI mismatch`  | The redirect URI sent by wg-easy is not registered verbatim — compare with the panel's **Redirect URI** display.                                           |
| `invalid_client` from the token endpoint | Wrong secret, or the provider was created as a Public client (public clients cannot authenticate with a secret).                                           |
| Discovery/issuer errors in wg-easy logs  | The configured server does not match the discovery issuer. Use the exact issuer URL from the provider's OpenID Configuration URL, trailing slash included. |
| App does not stay signed in              | The app provider is missing the `offline_access` scope mapping, so Authentik issues no refresh token.                                                      |
